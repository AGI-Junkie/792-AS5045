# 板上轨迹存档（Flash）

状态：固件和上位机已实现，**只在 PC 模拟和上位机自测里验证过，没有上过板**。上板要确认的事项见第 7 节。2026-10-14 起是存档格式 version 2（32 份、按实际大小存储，proto=6）。

## 1. 做了什么

执行器仍然只读 RAM 里的 `g_traj`。Flash 里另存最多 32 幅**已经通过校验的轨迹**（每点 `q1`、`q2`、`ms`，6 字节），断电后还在；用的时候从 Flash 把它填回 `g_traj`，不用再把几百个节点逐个传一遍：

```text
上传 → RAM 里校验完整 → 存入 Flash 槽位
                          ↓ 断电后仍在
重新上电 → 使能、回零/人工参考 → 移到图形起点
         → 从 Flash 加载到 RAM（重新过全部校验）→ 点“执行图形”
```

- 存的是**轨迹点**，不是 `traj_t`（里面有运行状态、计时），也不恢复机械参考、使能或运行状态。
- 轨迹点之外，板上还可以带一段**描述**（做这幅图用的设置，见第 5a 节），所以换一台电脑连上板子，也能看到槽里是什么图、把参数填回去。没有描述的槽（旧固件存的、或描述放不下）显示为“别处存的图形”，只能清除；上位机另在本机记一份（`%LOCALAPPDATA%\TwoLinkCommissioning\board-slots.json`），给没有描述的槽起名，板上有描述时以板上的为准。

## 2. Flash 布局（存档格式 version 2）

| 地址 | 大小 | 用途 |
|---|---:|---|
| `0x00000–0x1FFFF` | 128 KB | 程序、常量、RAM 初值（现在用约 52 KB） |
| `0x20000–0x2FFFF` | 64 KB | 存档 A 区（256 行） |
| `0x30000–0x3FFFF` | 64 KB | 存档 B 区（256 行） |

一个区保存当前完整存档，另一个区留给下一版。区的第 0 行是**提交行**，其余 255 行（63.75 KB）放记录，一份接一份、每份从行首开始，**只占自己需要的行**：

```text
提交行：0 magic u32 "TRJS"  4 version u16 (=2)  6 contract u16  8 gen u32  12 records u16  14 usedRows u16
        16 bankCrc u32（第 1..usedRows 行，整行）  20 headCrc u32（覆盖 0..19）；其余 0xFF
记录：  0 slot u16  2 count u16  4 seq u32  8 durationMs u32  12 dataCrc u32（节点流）  16 metaLen u16  18 0xFFFF
        20 headCrc u32（覆盖 0..19）；然后 metaLen 字节描述、count × 6 字节节点，补 0xFF 到行尾
```

- 一份记录占 `ceil((24 + 描述字节 + 节点数 × 6) / 256)` 行：485 点无描述 12 行，2048 点加 256 字节描述 50 行。一个区最多 32 份（槽 0…31），同时受 255 行限制：满容量 2048 点的图能放 5 幅；短图可以放满 32 份。
- `dataCrc` 是节点流的 CRC-32/IEEE（和 zip、PNG 同一个），上位机对自己的计划算同一个值，就能认出“这幅图已经在板上”。
- `seq` 是这份记录**写入时的存档代次**：没改的记录在重写时原样复制、保留原 `seq`；新存或替换的记录拿新的代次。所以清空后再存同一槽也不会出现重复的 `seq`。
- `contract` 是关节角约定的版本（`TS_CONTRACT`）。改了坐标约定就加一，整个存档作废，而不是画错。
- 上电时两个区都整区校验（提交行、整区 CRC、逐份记录头：槽号不重复且在范围内、点数 2…2048、描述不超过 256 字节、长度不越界、份数和行数对得上），选代次较新的有效区（按 2^32 取模比较），记录的位置和摘要放进 RAM 里的 32 项目录（约 0.8 KB）。都无效时存档为空。

## 3. 保存为什么断电安全

保存、替换、清空都是**把整个下一版存档写进另一个区**，当前区一行都不碰：

0. 写之前先逐份核对要保留的记录（每个前台循环一份）：节点和它的 CRC 不符（上电校验之后 Flash 又变了）就失败、什么都不写，回 `TRAJ_STORE failed: slot <n> is damaged (clear it)`；清除那个槽就能继续。加载同样先核对节点 CRC，不符就拒绝；
1. 把另一个区的提交行写成全 0xFF（作废），读回确认；
2. 把要保留的记录从当前区逐行复制过去（替换和清空就是不复制那个槽），每行读回核对；
3. 保存时接着写新记录（头、描述、节点），每行读回核对；
4. 最后写提交行（代次加一、份数、已用行数、整区 CRC），读回确认；
5. 成功后才换用新区并回 `last=saved` / `last=erased`。

每个前台循环只写一行。任何一步断电或写失败，当前区还在，重启后就是旧的完整存档；提交行是单独一行、最后写，前 24 字节就是全部字段和它的 CRC，所以提交行写了一半时要么整版新存档生效（它之前的行都已读回核对过），要么无效。模拟里对新增、替换、清空三种操作的**每一个写操作**都试了“整行没写进去”“只写了一半”和“写入错误”，重启后存档必然是旧版完整或新版完整。

代价：每次保存都重写整个存档，耗时随已用行数增长（最多 257 次写行；第一次上板要量）。另一个区里的上一版只在当前区损坏时作为后备：整区 CRC 不过时退回上一版，**会丢掉最后一次的改动**，但不会出现半份存档。描述损坏也是整区损坏（旧格式里只丢描述）。提交行写入时恰好断电（前半行已写入）时，设备本次报“失败”，重启后看到的却是新版；主机在任何失败后都会重读清单。

放不下（替换同一槽时它原来的行算可用）就拒绝：`TRAJ_STORE refused: archive full`，什么都不写。清空空槽不写 Flash。

## 4. 链接脚本：怎么保证程序不会长进存档区

只写一个地址常量不够，必须让链接器知道那段不能用。`DRV8825.cydsn/cm3gcc_trajstore.ld` 是 Creator 生成的 `cm3gcc.ld` 的副本，只改三处：`rom` 缩到 128 KB（程序长大会在链接时报错，不会悄悄覆盖存档）、声明 `store` 区、把原来用 `LENGTH(rom)` 表示“Flash 末端”的两处换成 `CY_FLASH_TOP`。

在工程里：Project → Build Settings → Linker → General → **Custom Linker Script**，Debug 和 Release 都填 `cm3gcc_trajstore.ld`（`DRV8825.cyprj` 里已经设好）。Creator 升级后要和新生成的 `cm3gcc.ld` 对一遍。

**保险**：固件用弱符号 `__trajstore_start` 判断自己是不是用这个脚本链接的（`TS_LINKED()`）。用默认脚本链接时它是 0：LINK 行报 `traj_store=0`，type 12/13 全部拒绝，写 Flash 的函数也拒绝任何存档区之外的偏移——最坏情况是功能关掉，不会写坏程序。

核对镜像（`build-release.ps1` 会自动检查前两项）：

- `DRV8825.map` 里有 `store 0x00020000 0x00020000` 和 `0x00020000 __trajstore_start`；
- `arm-none-eabi-nm DRV8825.elf | findstr trajstore` 看到 `__trajstore_start` 在 `00020000`；
- 程序最高地址（`.rodata` 末尾）远小于 `0x20000`。

## 5. 命令（详见 [PROTOCOL.md](PROTOCOL.md)）

- **type 12**（控制序号）：q1 = 槽位 0…31（查询可用 -1 = 全部：先回 `TRAJ_DIR`（份数、已用/剩余行、哪些槽有图形），再分步发有图形的槽各一行），q2 = 1 查询 / 2 保存 RAM 里的轨迹 / 3 清空。保存/清空要求静止；保存期间 PTP、点动、回零、范围/速度配置都被拒；任何停止、使能、新上传会丢掉 RAM 轨迹，保存随即中止，旧存档不动；放不下回 `refused: archive full`。
- **type 13**（PTP 序号）：加载。要求已使能、已回零或人工参考、静止，且**两轴正好在存档轨迹的起点**；节点逐个过 `traj_begin`/`traj_push` 和**当前**的关节范围、速度、加速度，任何一项不满足就拒绝并清空 RAM 轨迹。**CRC 对只说明字节没坏，不说明轨迹符合当前设置。**
- 回执行：`TRAJ_SLOT …`、`TRAJ_STORE state=… rows=… seq=… last=… row_max_us=…`、`TRAJ_LOAD slot=… seq=… nodes=… duration_ms=… crc=…`。加载回执的 CRC 是实际加载节点流的 CRC-32/IEEE（8 位大写十六进制），必须与预览计划一致；（version 2 起 `seq` 不再复用，CRC 仍然必须核对。）缺失或不符时，上位机改为上传预览计划。主机与固件须配套 `proto=6`。LINK 里 `traj_store=<n>`。

## 5a. 描述（type 14 和 type 12 op 4）

设备不读描述，只保管：最多 256 字节（`TS_META_MAX`），主机决定内容。上位机存的是这幅图的设置文本，只保留能还原图形的那几项，格式同实验记录里的 `key=value;`：

```text
shape=2;branch=0;L1=180;L2=176.38;x=330;y=0;a=12;b=7;c=;rot=0;scale=1;dir=ccw;v1=4;v2=3;a1=8;a2=6
```

- 保存前，上位机用 type 14 把它按 4 字节一块发给设备（约 30 块，每块 36 个线上字节，没有逐块回执），再发 type 12 保存。设备在保存时核对：块齐全、文本 CRC 对、描述里的**轨迹 CRC 等于实际写入的节点流 CRC**——最后一条保证描述不会配到别的图上。任何一条不满足，保存要么被拒绝（什么都没写），要么失败（旧槽不动）。
- 连上设备、读完清单后，上位机对每个有效槽发一次 type 12 op 4 读回描述（`TRAJ_SLOT` 行上没有任何关于描述的信息，所以不能靠它判断；没有描述的槽回 `len=0`）（一次一个槽；槽的 `seq` 或计划变了、槽被清空过才重读）。读失败（丢行、被拒绝），或状态行到了但描述行没到时，过一会儿再试，最多重试 3 次，之后这个槽仍列为“别处存的图形”，重连或重新保存才再读。
- 设置文本超过设备声明的字节数（`traj_meta`，现为 256）或含非 ASCII 字符时，保存照常进行但不带描述，保存完成的提示里会说明“没有存描述”，别的电脑上这个槽会列为“别处存的图形”。
- 点板上的行恢复参数时，描述必须完整（图形、逆解分支、位置、尺寸、变换、方向、两轴速度和加速度都在）：不像旧的运行记录，板上的描述不会用当前打开的图形补缺字段，否则点下去得到的是一组混合参数。缺字段的描述当作“没有可恢复的参数”，改读板上的节点。
- 手绘图形的原始笔迹放不进 256 字节，所以描述里只有“自定义轮廓”这个事实：在别的电脑上这样的槽不能恢复参数，但能读回节点、看到板上真实存的路径（见 5b）。

## 5b. 读回节点（type 12 op 5）

为了让“没有参数可恢复”或“按这台电脑的杆长重新算出来不一样”的槽也能被看到：设备把槽里的节点原样发回（一行最多 40 点，主机从第 0 点起逐行要，2048 点要 52 次，每次都等回执）。主机收齐后用整个节点流对槽的 CRC、点数和总时长，任何一项不符就不显示；读到一半发现槽的保存次数（`seq`）变了也放弃，并重读清单。

预览把节点连线（执行器在相邻节点之间每个关节走直线）画成虚线，按描述里保存的杆长画（没有描述就用这台电脑的，并在结果里说明），可以播放，不能导出；它只活到下一次预览或编辑。读的时候手臂和按钮锁定，不运动。

**读回的计划能不能执行**：节点收齐、核对过之后，还要过和规划出来的图形同一套检查（`ExecutionTrajectory.FromNodes` → `Validate`）：这台电脑当前框里的关节范围和肘范围、每轴速率和加速度、每段时长、起点静止。不改、不重新定时，要么原样接受，要么说明哪一项没过。

- **通过**：它成为屏幕上的计划（预览仍按保存时的杆长画）。把手臂移到起点后，“上传图形”变成“从板上加载”——计划的 CRC 就是槽的 CRC，走 type 13，秒级；点“执行图形”才会运动，不会自动开始。设备加载时还会按它**当前**的范围和速度再检查一遍，不通过就退回逐点上传同样的节点。
- **没通过**（例如保存时用的是更快的速度）：只能看，不能移到起点、上传或执行，提示里写明没过的那一项。手绘/自定义轮廓的槽也是这样走：读回的节点就是计划，不需要原始笔迹。
- 实验记录里这样的运行写成 `shape=10; … board_slot=N`，不会被当作能载回参数的图形。
- 杆长和动作：关节节点照原样执行（动作在关节空间）；杆长只影响 XY 的解释（预览、实验分析里的笔尖位置）。保存时的杆长与这台电脑不同时，结果文字里会写出两组数。

没做：把读回的路径变成可编辑的手绘草稿——会重新平滑、重新定时，和板上存的不是同一条。

## 6. 上位机怎么用

“最近运行”里的 ★ 现在表示“这个图形已存在板子上”（以前是本地收藏，已取消）：

| 操作 | 效果 |
|---|---|
| 连上设备 | 自动读清单和各槽的描述。带描述的槽（不论哪台电脑存的）列在“最近运行”最上面的“板上图形 · n/32”下：`★ 槽1：圆 · 69 点 · 16.6 秒`，本机的最近运行在它下面；板上已有的图不再重复出现在本机列表里。下方文字只列出有图形的槽，最后一行是 `板上图形 n/32 · 已用 x KB / 63.8 KB` |
| 点没有参数的槽，或重新算出的计划与板上不同 | 读回板上的节点（见 5b），预览画出板上真实的路径（虚线、可播放）。这台电脑当前的范围和速度也接受它时，它就是屏幕上的计划：移到起点、从板上加载、执行图形（手绘槽也一样）；不接受时只能看。点“检查并预览”回到这台电脑算的计划。固件不支持读回时，没有描述的槽不成为一行 |
| 点板上的一行 | 载入它存的参数（图形、尺寸、变换、两轴速度和加速度）并按**这台电脑**的杆长、范围重新规划，不运动。重新算出的计划与槽的 CRC 一致，就说明屏幕上是板上那条，“上传图形”变成“从板上加载”；不一致（杆长、范围或规划不同），提示里说明预览是这台电脑算的、不是板上那条。杆长和关节/肘范围从不被覆盖 |
| 点“存到板子”（“上传图形”“执行图形”旁边） | 把屏幕上**检查通过**的图形存到板上：有空槽且放得下就存进去；没有空槽或剩余空间不够时弹菜单（可滚动）选替换哪一个，只列出替换后放得下的图形；替换哪一个都放不下时不存，提示先清除别的图形（不会自动删除）。**不需要先执行一遍**——板子存的是设备持有的计划（上传完或执行完都行），设备上还没有这个图形时先上传再存（要求已使能、已回零、手臂在起点，和“上传图形”一样）；设备已经持有它时直接存，不要求在起点。板上已有这个图形、存档进行中、没读完清单、固件不支持时按钮不可点，提示里写明原因 |
| 点 ☆ | 载入这条运行的图形并检查，**上传**（要求已使能、已回零、手臂在起点，和普通上传一样），上传完成后**自动存入第一个空槽**（放得下时）；否则同上弹菜单选要替换哪一个。整个存档重写一遍，最多几秒，期间手臂和按钮锁定 |
| 点 ★ | 弹出“从板子清除槽 N”，点它才清除（一次误点不会清掉） |
| 点一条 ★ 运行 | 照常载入参数；因为屏幕上的图形与板上某槽的 CRC、点数、时长都一致，**“上传图形”变成“从板上加载”**，秒级完成，之后点“执行图形”才运动 |
| 板上的图形不能加载（范围/速度改过、数据损坏） | 自动改为普通上传，并在提示行说明 |

没有存档能力（旧固件、或没用存档链接脚本、或没连接）时，星标不可点，提示行说明原因。

## 7. 上板前后要确认的

- **version 2 不认旧格式**：烧录本来就会清空存档；旧的图形用上位机重新存。

- **烧录会清空存档**：Creator 生成的 HEX 把整片 256 KB 都写满（空的部分写 0x00），所以每次重新烧录固件，存档就没了。这不是新问题（任何整片烧录都这样），但要知道。
- **写一行要阻塞多久**：官方说明单次最长约 20 ms，期间读 Flash 的代码会被卡住。固件每个前台循环只写一行，并在 `TRAJ_STORE … row_max_us=` 里报告最慢的一行，**第一次上板必须看这个数**，同时看保存期间心跳间隔、`rx_overflow`、USB 是否掉线。保存期间主机不发别的命令；如果主机心跳在保存中断过久，deadman 会停机并中止保存（旧存档不受影响）。
- 每次保存/清空都重写整个存档：写行次数 = 保留的记录行 + 新记录行 + 2（作废、提交）。空存档存一幅 485 点的图 14 次，存档接近满时最多 257 次。**上板要量满存档时一次保存的总耗时、`row_max_us`、心跳间隔**，确认 deadman 和主机等待（12 秒无进度算失败；固件每 8 行报一次进度）都够。
- 断电恢复：存好后拔电重插，查询看到同一个槽、CRC 不变；移到起点后“从板上加载”再执行，应与直接上传的结果一致。
- `CySetTemp()`：每次保存/清空前调用；失败就拒绝保存。
