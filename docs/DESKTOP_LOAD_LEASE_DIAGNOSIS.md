# 2026-10-15 桌面负载下的 UI 租约停顿（DEADMAN）

## 现场记录

- `stage1-20261015-183458-442.log`：20:48:37.858 `HOST UI lease gap max=499 ms`，20:48:38.15 `STOP: DEADMAN host heartbeat timeout`（`phase=idle`、`hb_age_ms=251`），手臂在两次图形之间空闲。同一时刻操作员在用别的程序，自动化脚本点了“检查并预览”并通过 UI Automation 读取窗口。故障快照 `pre_fault.csv` 的上位机时间戳显示界面线程 37.207→37.563 s 停了 356 ms，37.564→38.141 s 又停了 576 ms，中间只处理了一次串口数据。随后一分钟内又有 470、557、209、324、696 ms 的停顿。
- `stage1-20261014-191008-108.log`：19:28:37 582 ms（手动操作中，空闲时 DEADMAN）；20:30:01 363 ms（窗口拖到另一块 DPI 不同的显示器）；改形状/速度字段时多次 200–270 ms。

200 ms 租约（`LeaseStopMs`）、250 ms 固件 deadman 和“心跳跟随界面存活”的设计不变。

## 复现方法

`TwoLinkCommissioning.exe --desktop-load-profile <输出文件>`：真实窗口和真实 Dispatcher，按现场 20:48 的状态块每 500 ms 一组、遥测 10 Hz；每 0.7 s 轮流做“检查并预览”、改 x、改速度、切换形状（圆 ↔ 多边形）；可选一个 UI Automation 客户端（订阅整窗的结构、名称、值、可用状态、边界、文本事件，并反复读取每个元素的名称、边界、状态、值和文本），在本进程或另一个进程（`--uia-client`）；CPU 负载由其他进程（`cmd` 空循环，每个占满一个逻辑核）产生。输出每个场景的 UI 租约最大间隔，以及每个超过 100 ms 的间隔里是哪些 Dispatcher 操作、窗口消息占了时间。不打开串口，不发电机命令。测量机为 20 个逻辑核。

## 测到的结果（改动前）

| 怀疑项 | 测量 | 结论 |
| --- | --- | --- |
| 检查并预览（重新规划） | 现场 7 个板上图形：规划 8–33 ms，加布局 4–21 ms（最大是 2503 点螺旋）；20 核全满时 60–122 ms | 不是 200 ms 级停顿的来源，未移出界面线程 |
| 改字段 | 只让计划失效，不重新规划 | 同上 |
| 只读的 UIA 读取（每轮读全部 ~290 个元素） | 租约间隔 ≤ 80 ms | 不是来源 |
| 订阅事件的 UIA 客户端 + 画布重绘 | XY 预览画布（最快 30 Hz）和误差曲线（10 Hz）每次重绘都清空后重建全部线条和文字；有客户端在听时，WPF 每次布局后为每个新文字块发名称/可用状态/结构事件。本进程客户端 15 s 内 9 000–12 400 个事件；未预热时间隔 219–780 ms；隐藏画布后事件降到约 2 900 个，反复出现的布局开销消失 | 主要可复现来源 |
| 首次有客户端订阅事件 | 进程内第一次订阅时有一次 200–560 ms 的布局（WPF 第一次为所有元素发事件，`DOTNET_TieredCompilation=0` 反而更长，说明主要是首次编译）；同一进程第二次订阅没有这次停顿。另一进程的客户端在全新进程里首次连接：5 次 78–212 ms，212 ms 那次是 `WM_GETOBJECT` 时一次 195 ms 的布局 | 每个进程一次，已在启动时提前付掉（见下） |
| 日志框 | 日志被选中/聚焦时从不裁剪；4 MB 时一次 UIA 连接的布局多 120 ms | 次要来源 |
| CPU 占满 | 20 个满负载进程、本程序 Normal 优先级：普通编辑 122 ms、检查并预览 60–110 ms；AboveNormal 时 ≤ 53 ms | 放大器 |
| 跨显示器移动 | 窗口是系统 DPI 感知（`GetWindowDpiAwarenessContext` = 1，可执行文件 manifest 无 dpiAware），换到 100% 的显示器时由 DWM 缩放位图，WPF 不按新 DPI 重新布局；150% ↔ 100% 之间程序化移动窗口 16–39 ms | 现场 363 ms 不是 DPI 重排；未复现（需要真实拖动标题栏，可能是拖动的模态循环或窗口换了显卡） |

## 改动

- `PlotCanvas`（`PlotView.cs`）：XY 预览画布和误差曲线在 UI Automation 里各是一个元素（保留原有中英文名称；误差曲线以图表标题为名称），不再把每次重绘的线条和文字暴露出去。画布上的文字本来就是重复的坐标、标注，计划和位姿信息仍在旁边的文本框里。
- 日志框：被选中/聚焦时裁剪推迟到 400 k 字符（以前是永不），裁剪后保留选区。
- 打开串口期间进程优先级为 AboveNormal，断开时恢复（只在原来是 Normal 时调整）。界面卡死时心跳照样停止，优先级只决定谁等 CPU。
- `HOST UI lease gap max=… ms` 后面附上这次最长间隔里是谁占着界面线程：最长的 Dispatcher 操作的优先级和耗时、操作总耗时、操作之外的时间、Send 调用数（UI Automation 读取）。`tools/check-log.py` 的匹配不受影响。下次现场停顿（例如 DPI 切换）可以直接看出是布局、我们的定时器、UIA 还是窗口消息。
- 启动预热：主窗口第一次渲染后，后台线程以 UI Automation 客户端身份订阅一次结构和属性事件、触发一次布局、再注销，把“第一个客户端”的编译和通告开销放在还不能连串口的启动阶段。全新进程里另一进程客户端的首次连接从 78–212 ms（一次 195 ms 布局）变为 59–128 ms，没有布局突发（剩下的最大值是一次检查并预览）；连接时的事件从 1 000–1 450 个降到约 600 个。预热失败只记一条跟踪信息，不影响功能。
- 闸门：`--self-test` 增加桌面负载回放：一半 CPU 被其他进程占满，进程内 UIA 客户端订阅事件并反复读取（预热后计时），10 s 内 UI 租约间隔低于 200 ms；并检查重绘后的两个画布不向 UI Automation 暴露子元素。

## 改动前后（同一台机器、同一回放，窗口在屏幕上，UIA 客户端预热后计 15 s）

| 场景 | 改动前：UI 租约最大间隔 / >120 ms 次数 / UIA 事件数 | 改动后 |
| --- | --- | --- |
| 空闲，无 UIA | 101.9 ms / 0 | 53.7 ms / 0 |
| 20 核全满，无 UIA | 64.1 ms / 0 | 33.3 ms / 0 |
| 空闲，本进程 UIA 订阅+读取 | 197.3 ms / 5 / 11 770 | 69.5 ms / 0 / 3 228 |
| 20 核全满，本进程 UIA | 176.7 ms / 2 / 11 446 | 65.4 ms / 0 / 1 896 |
| 空闲，另一进程 UIA | 72.8 ms / 0 / 398 | 46.5 ms / 0 |
| 20 核全满，本进程 UIA，AboveNormal | 142.2 ms / 2 / 11 737 | 47.7 ms / 0 / 1 904 |
| 20 核全满，另一进程 UIA，AboveNormal | 79.1 ms / 0 | 40.9 ms / 0 / 700 |

改动前的间隔几乎全是 `MediaContext.RenderMessageHandler`（布局及其后的自动化事件），改动后首秒之后没有超过 30 ms 的布局。上表是加启动预热之前测的；`--desktop-load-profile` 现在把另一进程客户端的首次连接也计入（从启动客户端开始计时），本进程客户端仍预热后计时（它首次订阅的编译只发生在本进程客户端身上）。另一进程客户端偶尔在自己的 UIA 调用里卡到 20 s 超时，客户端每读一轮就输出一次计数，卡住时用最后一次的计数。

闸门里的回放（10 个其他进程占满一半 CPU，本进程 UIA 预热后 10 s）：61.6 / 74.8 / 74.4 ms，加启动预热后 41.9 ms，均 0 次超过 120 ms。

## 没有做到的

- 现场 363 ms 的拖动停顿没有复现（不是 DPI 重排，见上表）；新日志字段会给出下一次的归因（布局、我们的定时器、UIA 还是窗口消息）。
- 预热只覆盖本进程能触发的路径；另一进程客户端首次连接时的 `WM_GETOBJECT` 处理仍在界面线程上，测到的最大值 128 ms。
- 只做了离线测量，没有上板，没有烧录固件。
